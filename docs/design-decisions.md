# Design Decisions

実装を今の形にした理由です。詳細な機能は [要件定義](./requirements.md) を見てください。

## 題材を「社内問い合わせの渋滞」にした

勤怠・経費・ToDo はどこにでもある。同じ質問の繰り返しは、小さな会社で起きていて、時給を置けば「いくら減るか」を面接でも話せる。Slack 全文クロールは権限と個人情報の問題が大きいので、手入力と貼り付けにした。

## 画面に説明文を置かない

「同じ質問が何回流れているか」は現場がすでに知っている。大きな見出しやメリットの文章は外し、ラベルと数字だけにした。言語切替で変わるのは UI 文言とチャンネル表示名。記録本文は変えない。

## JSON ファイルで、DB にしない

利用者は1オフィス、ホストは1プロセス。Postgres を置くとバックアップと運用が先に来る。`workspace.json` ならコピーがバックアップになる。サーバーレスは再起動で消えるので対象外と明記した。

## 分類はキーワード、埋め込みではない

デモと社内運用を同じコードで回すため、再現できる規則にした。未分類は失敗ではなく、設定に語を足す合図。チャンネルは分類キーに使わない（置き場所と中身を分ける）。

## チャンネルは `#社内` / `#社外` を固定 ID にする

表示だけ ja/en で変える。英語 UI で `#internal` と保存すると、日本語に戻したとき別チャンネルになるため。

## 集計はクライアント、保存はサーバー

保存の正はファイル。ランキングは読み込み後に計算するので、テーマを変えたら再記録なしで付け替わる。件数はオフィス規模なのでブラウザで足りる。

## 予測入力はテーマから出す

記録のたびにテーマ名を思い出さなくても、本文の途中でキーワードに寄せられる。分類精度より、書く摩擦を減らすため。

## PIN は任意の共有秘密

ユーザーアカウントは作らない。LAN に出すときの最低限。未設定ならゲートなし。

## 損失は仮定を隠さない

時給・吸収率・期間は設定画面にある。正確な会計ではなく、文書を書く優先順位のための概算。
